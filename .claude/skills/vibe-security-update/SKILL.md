# vibe-security-update

You are running a fresh sweep of vibe-coding-relevant security incidents and integrating findings into this repo. The repo is `vibe-coding-security/` and you are at its root.

## Output for the user (always include at end)

A 5-line summary:
1. Date of this sweep
2. # of new advisories added
3. # of existing advisories updated (status, IOCs, sources)
4. # of new sources discovered + added to priority list
5. Link to commit (if pushed)

## Accuracy bar (non-negotiable — read before writing anything)

A wrong-but-confident advisory is worse than no advisory: readers act on it, and the whole repo's credibility rests on every entry being verifiable. Past sweeps shipped **fabricated facts that read as real** — invented source URLs (wrong article slugs, a non-existent `github.com/Rickidevs/…` repo), a malformed `GHSA-langgraph-27794` (real format is `GHSA-xxxx-xxxx-xxxx`), a `GHSA-XXXX` placeholder, and yearless `CVE-44789` shorthand. None were caught until a manual audit weeks later. Hold this bar on every run:

1. **Cite only what you actually opened.** Every URL in a `## Sources` list must be a page you fetched this run. **Never guess an article slug, CVE number, GHSA id, version, or download count.** If you didn't open it, don't cite it.
2. **IDs must be canonical and well-formed.** `CVE-YYYY-NNNN` (≥4-digit sequence, with the year) and `GHSA-xxxx-xxxx-xxxx` (4-4-4). A malformed id is a fabricated id — look up the real one or drop the claim. `tests/test_advisory_ids.py` now fails the build on malformed ids; don't work around it, fix the id.
3. **Verify the identifier resolves before stating it as fact.** A CVE/GHSA → confirm on NVD or the GitHub Advisory Database. A package/version → confirm it resolves (`npm view <pkg> versions` / `pip index versions <pkg>`). A download count / "N packages" / blast-radius number → take it from a **primary** source (vendor IR post, researcher writeup, registry), not an aggregator's paraphrase, and only repeat a figure you saw stated.
4. **Two independent sources for any full advisory** (already required below); a single-source claim is `status: unconfirmed`, never dressed up as confirmed.
5. **Run the external-link checker on what you wrote:** `python tools/check-external-links.py advisories/<new-or-edited-file>.md`. It reports 404s and whether a Wayback snapshot exists — **404 + no snapshot = the URL never existed → fix or drop it.** Never cite (or archive) a malware/IOC/C2 domain.
6. **Date volatile facts.** EPSS/KEV membership, "as of" counts, "patched in X" — stamp the date so future readers know when it was true.

These are enforced by Step 6's gate (`build → validate → pytest`) plus the link checker. The gate is the floor, not the ceiling — the gate can't catch a plausible-but-wrong number; you can.

## Process

### Step 0 — Sync, then load state

**FIRST, sync to the remote — the repo is swept ~daily and a local checkout goes stale within days.** Skipping this wastes a whole sweep re-discovering incidents already published (this happened 2026-06-19: a sweep ran against a checkout ~15 sweeps behind `origin/main` and recreated every "new" advisory under duplicate filenames; the push was correctly rejected).

```bash
git fetch origin
git log --oneline HEAD..origin/main      # how far behind are we?
git checkout main && git pull --ff-only  # or: git reset --hard origin/main if local is throwaway
```

Then **check whether the data is already current**: read the `Last refreshed:` date at the top of `ALERTS.md` and the latest entry in `runs.log.md`. **If a sweep already ran today, stop** — report that the data is current and do not duplicate it. Only proceed if today's sweep hasn't happened.

Read these files (all required, *after* syncing):

- `ALERTS.md` — current active/recent/historical feed
- `advisories/README.md` — index
- `.claude/skills/vibe-security-update/source-priorities.json` — ranked sources
- `.claude/skills/vibe-security-update/runs.log.md` — prior runs

Set:
- `today` = current absolute date (YYYY-MM-DD)
- `t_24h` = today − 1 day

For each unique candidate incident pulled from results, decide:

**A. NEW ADVISORY** — write a new file in `advisories/` if:
- Package > 100k weekly downloads compromised, OR
- CVE in major AI coding tool, OR
- CVE in major AI-agent framework SDK (LangChain, Semantic Kernel, PraisonAI, OpenClaw, etc.), OR
- CVE in core vibe-coding web stack (Next.js, React, Svelte, Vite, Tailwind, FastAPI, Streamlit, Prisma, NextAuth.js, Supabase) with practical exploitation path, OR

- Cross-ecosystem worm (npm ↔ PyPI ↔ RubyGems with identical payload), OR

Use the template in `CONTRIBUTING.md`. Filename: `YYYY-MM-short-id.md`.

**B. UPDATE EXISTING** — append to an existing advisory if:
- Status changed (active → contained, etc.)
- New IOCs published
- New sources strengthen / correct the writeup
- Patched version released

Always bump `last_updated` in frontmatter when touched.

**C. SKIP** — log but don't write up if:
- Already covered in an existing advisory with no new info
- Not relevant to vibe coding audience (e.g., kernel CVE, generic enterprise vuln)
- Single unconfirmed source (need ≥2 independent for a full advisory)

### Step 6 — Run the deploy gate locally before committing (CLOSED LOOP — do not skip)

**The GitHub Pages deploy runs `build.py → validate.py → pytest` and fails the deploy if any step fails. Run the exact same gate locally and only commit if it is fully green.** Committing without this is what froze the live site for 2+ weeks (2026-06-04 → 2026-06-19): every daily sweep committed broken internal links, `validate.py` failed, and the site silently stopped updating while `main` kept advancing.

**Always run the date-update script FIRST:**

```bash
python tools/update-alerts-date.py  # ensure ALERTS.md date is current
python site/build.py        # must succeed
python site/validate.py     # must print "All checks passed."
python -m pytest tests/ -q  # must be all-green (matches the deploy's `pytest tests/ -v`)
```

If any step fails, **fix it before committing** (or revert the offending advisory). Common failure modes seen in practice:

- **Broken internal links (the #1 cause).** Advisory bodies must link **only to playbook/prevention docs that already exist** — run `ls playbooks/ prevention/` and link those exact filenames. Do **not** invent a new `playbooks/if-you-foo.md` and link it: if no existing doc fits, link the closest existing one (`if-you-installed-a-bad-npm-package.md`, `if-an-mcp-server-was-malicious.md`, `auditing-a-vibe-coded-repo.md`, `rotating-cloud-credentials.md`, `prevention/ci-cd-hardening.md`, etc.) and log the wanted-but-missing playbook to `BACKLOG.md` instead of dangling-linking it.
- **Fabricated external source URLs (a real, recurring problem).** `validate.py` does **not** check external links, so an invented citation URL ships silently. Do **not** guess article slugs or GHSA IDs — paste the **exact URL you actually opened in the sweep**. A 2026-06-19 audit of the 2025 advisories found 6 fabricated source URLs (wrong BleepingComputer/CyberSecurityNews slugs, a non-existent `github.com/Rickidevs/...` repo, and a malformed `GHSA-langgraph-27794` — real GHSA IDs are `GHSA-xxxx-xxxx-xxxx`). For any new advisory, run `python tools/check-external-links.py advisories/<the-new-file>.md` — it flags 404s and tells you whether a Wayback snapshot exists (no snapshot + 404 = the URL never existed → fix or drop it). Never link a malware/IOC/C2 domain (live or archived).
- **llms.txt size caps** (`tests/test_llms.py`) overflow as the corpus grows — prefer trimming historical-status advisories from `llms-full.txt`/`llms-ctx.txt` at build time; bump the caps (with a dated comment) only as a stopgap.
- **`status` enum** — valid values are `active | contained | patched | mitigated | ongoing | historical | unconfirmed` (use `unconfirmed` for single-source incidents).

Then the lightweight checks: frontmatter complete on new files; `ALERTS.md` parses; `advisories/README.md` has a row per advisory; no secret/PII pasted in.

### Step 7 — Commit + push

```bash
git config user.name "pranava0x0"
git config user.email "2497510+pranava0x0@users.noreply.github.com"
git add -A
git status --short
# If anything changed (only after Step 6 is fully green):
git commit -m "sweep YYYY-MM-DD: N new, M updated"
git fetch origin && git rebase origin/main   # a daily sweep may have landed mid-run
git push
```
The `git config` lines are local (repo-scoped), not `--global` — a cloud-run sweep has no pre-existing identity and would otherwise commit as its own default bot account (this is also why commit messages must never carry a `Co-Authored-By:`/`Claude-Session:` trailer — see CLAUDE.md's git discipline section).

If the push is rejected (non-fast-forward), a sweep landed while you worked — `git fetch && git rebase origin/main`, re-run Step 6, then push. **Never force-push.** After pushing, confirm the deploy actually goes green (`gh run watch` on the "Deploy site to GitHub Pages" workflow) — a successful push but failed deploy means the live site is still stale.

If nothing changed (zero new, zero updated), still commit the `runs.log.md` + `source-priorities.json` updates with message: `sweep YYYY-MM-DD: no new incidents`.

## Source-priority semantics

The `source-priorities.json` schema:

```json
{
  "version": 1,
  "last_updated": "YYYY-MM-DD",
  "notes": "Higher weight = query first / trust faster. Cap 20. Min 1.",
  "sources": {
    "<domain>": {
      "weight": <int 1-20>,
      "hits": <int>,
      "last_hit": "YYYY-MM-DD" | null,
      "ecosystems": [<str>...],
      "tier": "vendor" | "research" | "aggregator" | "independent" | "official"
    }
  }
}
```

Use `weight` to:
- Pick top 10 sources for the `allowed_domains` filter in deep-tier queries
- Decide whether a single-source claim is trustworthy (weight ≥ 12 = OK to start a draft; lower = wait for second source)

## Constraints & cautions

- **Don't fabricate.** If a candidate incident doesn't have ≥2 independent sources, mark it `status: unconfirmed` in a new advisory and link only the sources you have. Do not invent IOCs, package names, or version numbers.
- **Auto-generated vulnerability-database pages (SentinelOne, cvedetails.com, etc.) sometimes pair a real CVE with the wrong GHSA ID, or vice versa — verify the pairing, not just the existence of each ID.** A 2026-07-01 sweep found a third-party vulnerability-DB page confidently citing `CVE-2026-42573` alongside `GHSA-8266-84wp-wv5c` — but fetching that GHSA directly showed it was a *different, unrelated 2024 Svelte XSS advisory* (`CVE-2024-45047`). The real pairing (`GHSA-rcqx-6q8c-2c42`) only surfaced on a second, more targeted search and was confirmed by fetching the GitHub Advisory Database page directly. **Never cite a CVE+GHSA pairing from an aggregator's prose — fetch the GHSA URL (or the NVD page) yourself and confirm the CVE ID printed on that exact page matches.** This is the same discipline as verifying a CVE resolves on NVD, just extended to the GHSA↔CVE cross-reference specifically, since that cross-reference is where secondary sources most often drift.
- **Verify dates against `today`.** Use `Today's date is YYYY-MM-DD` from the system context as ground truth, not the model's intuition.
- **Cap output.** If a sweep finds more than 10 candidate incidents, prioritize by severity × audience overlap with vibe coders. Log skipped ones in `runs.log.md` under "Notes: deferred".
- **Don't touch playbooks/prevention** in a routine sweep — those are evergreen. If you find a new attack pattern that warrants a new playbook, flag in `runs.log.md` under "Notes: playbook backlog" and let a human decide.
- **Don't auto-resolve status to `patched`** unless a vendor explicitly says so in a primary source.
- **Treat AI-agent framework CVEs as time-critical.** As of 2026-Q2, baseline disclosure-to-exploit is < 4 hours (per Sysdig honeypot data on PraisonAI). Prioritize these in triage and write them up same-day even if only 2 sources are available.
- **Cross-link cross-ecosystem worms — and Rust/Crates.io is now in scope.** When the same threat actor or payload appears in multiple ecosystems, cross-link the advisories explicitly (see Mini Shai-Hulud: TanStack ↔ PyTorch Lightning). Don't let the npm advisory and the PyPI advisory live in isolation. The campaign list now routinely spans **npm (`postinstall`) ↔ PyPI (import-time exec) ↔ Crates.io (`build.rs` build script)** — TrapDoor (May 2026) shipped all three from one actor in timed waves. When you see a cross-ecosystem stealer, check whether there's a Rust crate arm using `build.rs`, and whether the same campaign marker / GitHub account / Gist exfil endpoint appears across registries.
- **AI-agent config + skill files (`.cursorrules` / `CLAUDE.md` / `AGENTS.md` / `SKILL.md`) are a write-target, not just a read-target.** Earlier incidents *read* AI-tool config to steal creds (Bitwarden CLI AI-tool collector; Nx Console `~/.claude/settings.json` theft). TrapDoor (May 2026) inverts it: a malicious package **writes a hidden prompt-injection instruction into the repo's `.cursorrules` / `CLAUDE.md`**, hidden with **zero-width Unicode**, so the developer's *own* agent re-runs the attack on its next invocation (exfiltration disguised as an "automated security scan"). This fuses the GlassWorm steganographic-Unicode technique with AI-config-as-persistence/re-infection. The class has been formalized by the **Cloud Security Alliance "Agent Context Poisoning: SKILL.md and the New AI Supply Chain Attack Surface"** research note (2026-05-06) — payloads are natural-language behavioral instructions interpreted by models at runtime, not machine code, so static analysis and sandboxing don't catch them. Triage cues: on any supply-chain or repo-compromise finding, ask **"did it touch an agent-instruction file?"**; offer the grep-for-invisible-Unicode heuristic over `.cursorrules`/`CLAUDE.md`/`AGENTS.md`/`SKILL.md`/`.github/copilot-instructions.md`/`.windsurfrules`; and advise readers to keep those files in version control and diff them on every dependency change. This is a vibe-coding-specific surface — write such incidents up even when the headline is "another crypto stealer," because the AI-config persistence is the part our audience won't see coming.
- **Decorator-as-documentation pattern.** Watch specifically for vulnerabilities where an SDK annotation (`[KernelFunction]`, `@tool`, `@function_tool`, FastAPI's `@app.get`) is treated as documentation rather than a security boundary. This is now a known recurring class. When you see one, look for sibling vulnerabilities in the same SDK.
- **"Two parsers, one string" class (argv-smuggling + resolver disagreement + reconstructed-URL disagreement + check-vs-effect scope disagreement).** A recurring root cause: two components disagree on how to interpret the same value, and the security check runs on the *wrong* interpretation. Four known shapes now: (1) **Argv-smuggling / pre-parser** — an "eager" pre-parser walks `process.argv` for a flag (Claude Code's `eagerParseCliFlag`, Cursor's auto-run built-in handling) without tracking whether the matched string is itself the *value* of another flag, so an attacker controlling any argv element (deeplink, URL handler, MCP tool reply) smuggles arbitrary flag values. (2) **Matcher-vs-resolver disagreement** — an allowlist matcher and the OS/network resolver disagree on where a hostname ends, e.g. Claude Code's **SOCKS5 null-byte bypass** (`attacker.com\x00.google.com` passes the `.google.com` suffix check, the OS truncates at `\x00` and dials `attacker.com`, May 2026). (3) **Reconstructed-URL vs canonical-scope disagreement (host-header bypass)** — auth middleware reads a *rebuilt* URL (`request.url.path`, built from the `Host` header), the router reads the *canonical* ASGI scope path (`scope["path"]`), and a malformed `Host: foo?` re-splits the URL so they diverge — auth check runs on the wrong path while the protected endpoint still gets dispatched. **Starlette BadHost CVE-2026-48710 (May 2026)** is the framework-level case; downstream FastAPI/vLLM/LiteLLM/Python-MCP-SDK/TGI/OpenAI-proxy apps that authorize on `request.url.path` are vulnerable until they upgrade to Starlette ≥ 1.0.1 *or* refactor middleware to use `request.scope["path"]`. (4) **Check-vs-effect scope disagreement** — a deny-list / permission check binds to *current* (mutable) workspace/scope state, but agent input can rewrite that state before the operation runs, so the permission check evaluates against a *different* scope than the operation actually uses. **Windsurf CVE-2025-62353 (Oct 2025)** is the cleanest case: README.md prompt-injection rewrites Cascade's workspace path to `/`, then `write_to_file` targets arbitrary paths — **even with Auto-Execution OFF and `write_to_file` on the explicit deny list** (the deny check evaluated the rewritten scope). Same shape in any agent that lets agent-readable content mutate the scope of subsequent security checks. Note the discovery vector for BadHost — X41 D-Sec found it during an OSTIF-sponsored vLLM source-code audit, then realized it was a framework-level bug below vLLM — so an audit of any single downstream consumer of Starlette is implicitly an audit of the framework; flag this when sweep results name an Alpha-Omega / OSTIF audit. Same family as the InversePrompt cluster. **General triage cue: whenever the framework hands you both a canonical and a derived/reconstructed value of the same thing, the canonical one is the security boundary** — argv structure, post-canonicalization path, `scope["path"]`, the bytes that will actually hit `connect()`, the user-confirmed-at-session-start workspace path. **And: when a security check evaluates state that the operation it's gating can also mutate, the check is a permission honeypot, not a permission boundary** — bind security decisions to immutable scope, or re-check after any scope-changing input. Look for this whenever a value crosses a boundary between an in-app validator and a lower-level executor/resolver/dispatcher (argv parser, DNS, SOCKS, shell, path canonicalizer, ASGI router, workspace-scope manager).
- **AI-tool OAuth pivot pattern.** A breach at a third-party AI productivity tool that holds Workspace/Drive/GitHub OAuth grants is upstream of every cloud account that authorized it. The Vercel/Context.ai April 2026 incident is the first widely documented case; expect more. When triaging an AI-vendor breach disclosure, check what *other* platforms the breached tool had OAuth into — those are downstream victims.
- **Vendor patched ≠ patched.** If a vendor ships a fix that adds approval prompts or alerts but leaves the underlying trust-boundary intact (cf. ClaudeBleed v1.0.70), the correct status is `mitigated`, not `patched`. Don't auto-promote based on "vendor released a version." Read the researcher's follow-up and confirm the structural fix.
- **Silent patch (no CVE/advisory) ≠ no incident.** Some vendors fix security bugs quietly — no CVE, no advisory, no changelog note. Claude Code's network-sandbox **SOCKS5 null-byte bypass** was fixed in v2.1.90 (2026-04-01) with zero disclosure; it was the *second* silently-patched Claude Code sandbox bypass in ~5 months (prior: CVE-2025-66479). Implications for the sweep: (1) a "silent fix" disclosure (usually from the finding researcher's own blog weeks later) IS a writeable incident — set `status: patched` but call out the silent handling and the unprotected window; (2) advise readers to keep AI tools on `latest` and not pin old versions, because **"latest" carries undisclosed security fixes you can't see in release notes**. When a researcher blog says "they fixed it quietly," diff the fixed vs. prior version to confirm and record the vulnerable version range.
- **Connector-chaining lethal trifecta in desktop AI apps.** When an AI desktop app (Claude Desktop, Cursor, etc.) lets the model autonomously compose connectors, a low-trust *reader* connector (calendar, email, Drive, web) piped into a high-trust *executor* connector (a local MCP server that runs shell/code) collapses the lethal trifecta into one app — a malicious calendar event + a vague prompt ("take care of it") = zero-click RCE (Claude Desktop Extensions / DXT, CVSS 10.0, LayerX; Anthropic declined to fix as "outside our threat model"). Triage cue: on any AI-desktop/IDE finding, ask whether reader and executor connectors share one trust domain, and whether the vendor's response is "won't-fix / out of threat model" (→ `status: active`, not `mitigated`). Siblings: Supabase MCP lethal trifecta, Windsurf zero-click MCP. **Account-wide personalization/preference sync is also a reader connector, not just a UX setting.** [Pentera Labs' July 2026 finding](advisories/2026-07-claude-desktop-personalization-sync-rce.md) showed that Claude Desktop's account-synced personal preferences are themselves a low-trust content channel: a prompt planted there (via a compromised Claude account, reached through an unrelated email/identity breach) loads silently on every device signed into that account and, chained to any command-capable connector, produces the same reader-into-executor RCE — Anthropic again called this "expected functionality." Triage cue: when evaluating an AI desktop/chat app's connector-chaining exposure, explicitly check whether personalization, custom-instructions, memory, or any other account-wide synced-settings feature can carry attacker text into the same autonomous-execution path as calendar/email/Drive connectors — it usually can, and vendors often haven't threat-modeled it as a "connector" at all.
- **AI-agent → AI-agent supply chain.** Recurring: one compromised AI tool installs a second AI agent on victims (Clinejection → OpenClaw via npm postinstall; Comment and Control → exfil via Claude Code Sec Review). When you find a compromised AI dev tool, check whether the payload installs *another* known AI agent — cross-link both advisories.
- **Provenance is identity, not integrity.** Supply-chain worms now defeat provenance attestation in two ways: (1) hijacking a real release pipeline mid-build so the *legitimate* pipeline signs a malicious artifact (TanStack/Mini Shai-Hulud, May 11 2026 — first valid SLSA provenance on malicious npm), and (2) **self-minting cryptographically valid Sigstore attestations** with an ephemeral EC keypair + OIDC identity token, so every republished package shows a green "verified provenance" badge and passes standard verification (@antv/durabletask wave, May 19 2026). A green provenance/SLSA badge proves *who* built an artifact, **not that it is safe** — never treat it as a clean signal. Look for this whenever a worm "republishes under legitimate maintainer identity."
- **Poisoned IDE/editor extension as a platform-breach vector.** A malicious version of an editor extension (VS Code / Cursor / Windsurf / Open VSX) on a single developer's machine is a foothold into every repo and credential that editor touches. TeamPCP used exactly this — the trojanized **Nx Console** extension (`nrwl.angular-console@18.95.0`, May 2026) — to exfiltrate ~3,800 of GitHub's *own* internal repos. Same trust-transfer shape as the Amazon Q wiper and postmark-mcp (build trust over clean versions, then push one poisoned release) and a sibling of the AI-tool OAuth-pivot class. When triaging an "AI/dev tool was compromised" story, check whether the delivery vector was an extension marketplace, and whether silent auto-update carried the payload. Note also: extension payloads now specifically target **AI-tool config** (`~/.claude/settings.json` and similar) alongside cloud creds — flag that as its own IOC.
- **Cross-incident credential chaining (trace the leaked token forward).** Stolen credentials don't stay in their original incident. The Nx Console compromise happened because an Nx contributor's GitHub token leaked in the *prior* TanStack/Mini Shai-Hulud wave, then got reused a week later to publish the poisoned extension, which became the foothold for the *downstream* GitHub internal-repo breach — three "separate" incidents that are one chain. Sweep discipline: when a wave dumps credentials, ask **"whose token was stolen, and what can it publish next?"** and proactively check the maintainers/orgs named in a credential-theft wave for follow-on registry/extension compromises. Cross-link the chain explicitly (token-leak advisory ↔ extension advisory ↔ breach advisory). **Credential cascades now have a documented infostealer-as-a-service intermediary:** [Megalodon](advisories/2026-05-megalodon-github-actions-mass-campaign.md) (May 2026) hit **5,561 GitHub repos in 6 hours** using stolen credentials, and Hudson Rock matched **~33% of affected accounts to known infostealer victims** — strongly suggesting the credentials came from the [GlassWorm](advisories/2025-10-glassworm-vscode-worm.md) ecosystem and were *re-sold* downstream. When you see a coordinated takedown (GlassWorm 2026-05-26 = CrowdStrike + Google + Shadowserver), expect a downstream credential-resale wave to follow within days from a *different* actor monetizing the harvest. **Hudson Rock + StealerCheck-style lookups against affected-username lists are now a primary correlation tool for the sweep** — when an aggregator names affected accounts, run them against the infostealer-victim corpus before attributing.
- **Source-repo compromise as a publish-time trust boundary.** The npm/PyPI account isn't the only publish-time boundary — the **GitHub source repo + its `.github/workflows/`** is the *other* one, and it's often weaker. [Megalodon](advisories/2026-05-megalodon-github-actions-mass-campaign.md)'s `@tiledesk/tiledesk-server` arm (npm 2.18.6 → 2.18.12, May 2026) is the cleanest worked example: the attacker never touched the npm account, just committed a single `.github/workflows/docker-community-worker-push-latest.yml` change (entire prior Docker-build workflow gone, replaced with `set +e; echo "..." | base64 -d | bash`), and the legit maintainer published from the poisoned source without spotting the swap. Sibling: [elementary-data](advisories/2026-04-elementary-data-pypi-ghcr-compromise.md) (Apr 2026, GitHub Actions script injection → forged signed release → real publish pipeline). Triage cue: on any package-poisoning finding, ask whether the entry point was the maintainer's **npm/PyPI token** *or* their **source repo `.github/workflows/` directory**. The signature pattern is a **single-file workflow change authored by a bot-named account** (`build-bot`, `auto-ci`, `ci-bot`, `pipeline-bot`, `dependabot[bot]`-lookalikes), especially one containing a base64-bash pipe or `workflow_dispatch` backdoor. The defensive pattern is **require signed commits + workflow-change code review on protected branches** (which would have failed verification for Megalodon's `build-bot`-authored commits).
- **Coordinated botnet takedown as a recognized advisory event class (`active` → `mitigated`, not → `patched`).** When CrowdStrike / Google / Shadowserver / law-enforcement-class actors disrupt a sweep-tracked campaign's C2, update the existing advisory's status to **`mitigated`** (NOT `patched` — the structural fix isn't on the vendor side) and document the takedown date and the disrupted channels. **Warn readers that the takedown does NOT uninstall malware, rotate stolen credentials, or undo downstream credential resale** — poisoned packages/extensions on disk and stolen creds in the wild are still live risks. The [GlassWorm 2026-05-26 takedown](advisories/2025-10-glassworm-vscode-worm.md) is the template: CrowdStrike Counter Adversary Operations + Google + Shadowserver Foundation hit all four C2 channels simultaneously (Solana blockchain memos + BitTorrent DHT + Google Calendar dead-drops + direct VPS IPs). The quad-redundant C2 architecture meant a less coordinated strike would have left survivors — when triaging future takedowns, **check whether ALL known C2 channels were disrupted simultaneously** before promoting status; partial disruption is a temporary reduction, not mitigation. Note: the [Megalodon wave](advisories/2026-05-megalodon-github-actions-mass-campaign.md) shows that credentials harvested before a takedown stay valuable downstream — the C2 may be dead, but the data it exfiltrated lives on forever in attacker-controlled archives.
- **AI-vendor code-signing-cert rotation as a recurring named-instance.** When a major AI vendor (OpenAI, Anthropic, Google AI Studio, etc.) is downstream of a supply-chain wave that touches **code-signing infrastructure**, the downstream impact is a *forced-update event* for every user of the affected desktop app. **OpenAI has rotated macOS signing certs twice in 5 weeks** (May–June 2026): [Axios](advisories/2026-03-axios-compromise.md) March 31 disclosure → May 8 revocation, and [TanStack/Mini Shai-Hulud](advisories/2026-05-tanstack-mini-shai-hulud.md) May 11 wave → June 12 revocation. Both involved a GitHub Actions workflow with access to macOS signing keys downloading a compromised npm dep through a **floating tag without `minimumReleaseAge`**. Affected products: ChatGPT Desktop, Codex, Codex-cli, Atlas. Triage cue: when a sweep result names "[AI vendor] employee compromised" or "[AI vendor] internal source repos accessed," **explicitly check whether code-signing keys or signing pipelines were exposed**, and look for an update-deadline mandate that will force every downstream desktop-app user to update by a specific date. Track these rotations in the advisory's downstream-impact table; users will hit "app stops working" breakage on the revocation date and ask for context.
- **Steganographic extension payloads + un-takedownable C2.** GlassWorm (Oct 2025 → 2026, recurring) hides its logic in **printable-but-non-rendering Unicode** (invisible to a human reviewer and to many diff tools) and pins C2 to a **Solana blockchain memo** (a censorship-resistant dead-drop) backed by direct-IP + Google Calendar fallbacks — so takedowns can't reach the control channel and the worm self-reseeds with every set of stolen publish creds. When triaging an extension/worm story, look for "invisible Unicode," "blockchain C2," "Open VSX," and "self-propagating," and offer a detection heuristic (grep for zero-width / variation-selector / bidi code points in extension source).
- **Incomplete fix ≠ patched.** A vendor shipping a version labeled "fixed" doesn't mean the hole is closed — confirm against a researcher's follow-up. Langflow 1.8.2 was widely reported as the CVE-2026-33017 patch but remained exploitable (JFrog); only 1.9.0 actually fixed it. When a "patched" version exists, search "{tool} {CVE} still exploitable / patch bypass / incomplete fix" before setting `status: patched`.
- **AI-agent skill/plugin marketplace poisoning.** AI agents now ship their own community "skill"/plugin marketplaces — **ClawHub** for OpenClaw (formerly Clawdbot/Moltbot), plus Claude Code skills, MCP registries, and the like. These are the npm/Open-VSX of the agent world and are usually **open-by-default**: ClawHub's only publish gate was a GitHub account one week old. ClawHavoc (Koi, Feb 2026) flooded it with **335+ malicious skills** (of 341/824+ found) that use **fake prerequisites** to drop Atomic Stealer (AMOS). Installing a skill is functionally `curl | bash` with the user's privileges. Triage cue: treat any "agent skill / plugin / extension marketplace" the same as a package registry — query "{agent} skills marketplace malicious / {marketplace} stealer," count it as supply-chain (not a product CVE), and write it up separately from any product-vuln advisory for the same agent (cf. ClawHavoc vs. OpenClaw "Claw Chain" CVEs). Watch for **fake-prerequisite** social engineering and **macOS password-prompt (osascript) → AMOS** as recurring IOCs. **It's a class, not one campaign / one site:** Snyk's "ToxicSkills" audit (May 2026) spanned **ClawHub *and* skills.sh** (3,984 skills) and found prompt injection in 36% + 1,467 malicious payloads — so rotate *multiple* skill registries, not just ClawHub. Two extra IOC/heuristic cues this surface taught us: (a) **runtime-fetch evasion** — ~3% of skills (21% of malicious ones) fetch-and-execute remote content at install/run time, so the published skill passes review and flips malicious later; "scan-on-publish clean" is **not** safety. (b) **"skill scanner" tools are themselves a target** — distrust a scanner badge and the scanner binary alike. A **"ToxicSkill"** = looks benign in static review but the *agent executing it* is the gadget that turns it malicious.
- **Open-sourced/leaked worm → commoditized copycat wave.** When a threat actor *publishes the working source* of a supply-chain worm and/or runs a paid "biggest attack" contest (TeamPCP open-sourced Mini Shai-Hulud on 2026-05-12 + a $1,000 BreachForums competition), the barrier to a Shai-Hulud-class attack collapses to "clone the repo, swap the C2 key." Expect a long tail of **low-skill clones** within days (chalk-tempalte, axois-utils, etc.), often **typosquats** of popular packages, with **diversified payloads beyond credential theft** — Golang DDoS botnets (Phantom Bot), persistence (Windows Startup / Linux scheduled task). Triage cues: low download counts but novel actors; **disposable-tunnel C2** (`*.lhr.life` / localhost.run / ngrok / trycloudflare) as an IOC; the planted GitHub-repo marker ("A Mini Sha1-Hulud has Appeared"). Write the copycat wave up *separately* from the original campaign and cross-link — the actor and trigger differ (deliberate release, not maintainer compromise). **Updated 2026-06-02 — three documented copycat waves so far in three weeks, and the third (Miasma) escalates:** (1) [`deadcode09284814` typosquats](advisories/2026-05-shai-hulud-copycat-wave.md) — low-skill verbatim clones, ~2,700 downloads; (2) [TrapDoor](advisories/2026-05-trapdoor-cross-ecosystem-stealer.md) — cross-ecosystem npm+PyPI+Crates.io + `.cursorrules`/`CLAUDE.md` poisoning; (3) **[Miasma](advisories/2026-06-miasma-redhat-cloud-services-compromise.md)** — landed on a major *legitimate* npm scope (`@redhat-cloud-services`, 32 packages / 96 versions / 72-second burst), with **Greek-mythology theming replacing Dune markers** (breaks existing blue-team yara rules and SIEM queries that match the original Dune string set) and **new GCP/Azure cloud-identity collectors** added. Triage rule: when you find a Mini-Shai-Hulud-derived payload, *don't* set status `historical` just because it's "another copycat." The copycat trend is the story — each wave adds a novel primitive. When grepping for IOCs, **search for the *family*, not the *strings*** — `kralizec` and `phibian` will miss `spartan` and `miasma`.
- **AI-vendor-host camouflage exfil.** [Miasma](advisories/2026-06-miasma-redhat-cloud-services-compromise.md) (Jun 2026) is the first sweep-tracked wave to disguise stolen-credential POSTs as **outbound HTTPS to a real AI-vendor API host** — `https://api.anthropic.com:443/v1/api` (note: the `/v1/api` path doesn't exist, but the *request* itself carries the exfil payload; the 4xx response is irrelevant). This is the **DNS-baseline-normal counterpart to disposable-tunnel C2**: every org running Claude Code / Cursor / Anthropic API integrations already has outbound to `api.anthropic.com` allowed, monitored *only* for response codes, and not flagged as anomalous in egress logs. Expect the technique to spread to **`api.openai.com`, `generativelanguage.googleapis.com`, `bedrock-runtime.*.amazonaws.com`, `api.cohere.com`, `inference.huggingface.co`** — any AI-vendor host that's baseline-normal in dev egress. Triage / detection cues: (1) on any "credential-theft / exfil" finding, **look at the destination host** — if it's an AI-vendor API host on a non-existent path, that's the camouflage primitive; (2) recommend defenders **alert on outbound HTTPS to AI-vendor API hosts from workloads that aren't the AI tool** (CI runner that doesn't host Claude / Cursor / etc.) and on **non-2xx response patterns** to those hosts (real AI-tool traffic almost always succeeds, exfil camouflage almost always 4xx because the path is fake); (3) when writing up future waves, *check the destination host* and call out the camouflage pattern even when the rest of the wave looks routine — this is now a named technique, not a one-off.

- **`binding.gyp` / Phantom Gyp is a new install-time execution primitive that `--ignore-scripts` does NOT block.** The [Phantom Gyp wave](advisories/2026-06-phantom-gyp-miasma-wave4.md) (June 2026, fourth Miasma/Shai-Hulud copycat) established `binding.gyp` + node-gyp native-build as an install-time code-execution path that is **not suppressed by `npm install --ignore-scripts`**. (6) **import-time inlined self-executing code (bundled payload, no remote fetch)** — the [jscrambler compromise](advisories/2026-07-jscrambler-npm-preinstall-infostealer.md) (July 2026) is the clearest documented case of an attacker *pivoting primitives mid-campaign against the same package*: the first three malicious releases used a `preinstall` hook (blocked by `--ignore-scripts`), and the next two moved the identical loader logic into `dist/index.js` itself as self-executing code that fires on `require()`/import — distinct from primitive (5) because the payload (a 7.8 MB obfuscated binary container) ships *inside the package tarball*, not fetched remotely at runtime. **Triage cue:** when a compromised-package advisory lists multiple malicious versions in sequence, check whether later versions changed the *trigger mechanism* (hook → import-time) rather than just the payload — that shift is itself a signal the attacker is evading a specific detection/mitigation, and it means "I use --ignore-scripts" is not a sufficient answer to "am I safe" even for packages already vetted at the hook level. **Triage cue:** any npm package that includes `binding.gyp` but is not a well-known native addon (node-sass, bcrypt, sharp, fsevents, canvas, grpc, leveldown) should trigger review. When advising on Phantom Gyp / binding.gyp findings: recommend `npm update` to ≥ 11.16.0 + `allow-scripts=false` in `.npmrc`, and npm v12 adoption as the permanent fix for those two primitives specifically. **Add the Tier-A query "npm v12 allowScripts bypass {today.year}" starting this sweep** (npm v12 has now shipped) to catch any regression or bypass against the new default.

Extended list of camouflage host classes: (1) AI-vendor API hosts (`api.anthropic.com`, `api.openai.com`, `generativelanguage.googleapis.com`); (2) error-monitoring / APM webhooks (Sentry `store`, DataDog agent, New Relic, Honeycomb, OpenTelemetry collector); (3) CDN/analytics endpoints (Cloudflare analytics, Segment, Mixpanel). **Detection cues:** (a) alert on outbound `POST` to monitoring-service hosts from workloads that don't run the monitoring agent; (b) flag non-2xx responses to Sentry/APM hosts at unexpected intervals (real telemetry is batched; exfil camouflage tends to fire once at `build.rs` or `postinstall` time); (c) when writing up a `build.rs`/`postinstall` exfil finding, **look at the destination URL format** — if it matches a developer-monitoring service webhook, call out the camouflage technique by name and add it to the IOC list. **Sweep discipline:** on any new `build.rs` or install-hook exfil report, run a regex match on the destination URL against known monitoring-service API patterns before accepting "unknown C2" as the description.
- **Agentjacking / MCP data-stream injection — user-controlled MCP tool output is an indirect prompt-injection delivery surface.** [Agentjacking](advisories/2026-06-agentjacking-sentry-mcp-injection.md) (Tenet Security, June 2026) disclosed that AI coding agents (Claude Code, Cursor, Codex) routinely read user-controlled content via MCP tools and execute injected instructions with an **85% exploitation rate** in controlled experiments (2,388 orgs exposed in the measured campaign). The injection surface is Sentry error events (issue bodies, breadcrumbs, stack-frame locals), but the class applies to **any MCP server that returns user-controlled data**: GitHub Issues/Comments, Slack messages, Notion pages, Linear tickets, Jira issues, HubSpot notes, Gmail/Outlook content. The root cause: an AI agent applies *less skepticism* to "data" returned by an MCP tool than to instructions in a system prompt, even though both arrive in the same context window. Unlike fetched web pages (where Claude Code has explicit tool-approval semantics), MCP tool results are treated as implicitly trusted. **Triage cues for new MCP advisories:** (1) any widely-used MCP server that returns user-controlled content (not just developer-written config/data, but content that any end-user of a connected system can control) should carry an Agentjacking risk warning in its advisory; (2) add `"AI agent MCP data injection prompt injection {today.year}"` and `"Agentjacking {today.year}"` as Tier-A queries; (3) when a vendor's MCP server connects to a collaborative platform (Slack, Notion, Linear, GitHub), ask: "can any user with write access to the connected platform plant instructions in content that the agent will read?" — if yes, that's an active Agentjacking surface; (4) mitigation triage: check whether the MCP server has an output sanitization option; check whether the agent has a "distrust MCP output" mode or per-tool approval; recommend removing high-risk MCP servers (Sentry, Slack, email) if the agent runs in `--dangerously-skip-permissions` mode; (5) report to `source-priorities.json` as `tenetsecurity.ai` (weight 10) — the primary source class for this finding.
- **"Lies in the Loop" (LITL) — approval-dialog padding hides malicious commands below the visible fold.** Checkmarx Zero (June 2026) disclosed that AI agent approval dialogs (Claude Code, VS Code Copilot) render markdown and can be manipulated by attacker-controlled prompt injection to insert hundreds of blank lines or zero-width Unicode characters, pushing the malicious part of a compound shell command below the visible dialog area. The developer sees and approves what looks like a safe command; the hidden payload (below the scroll) runs simultaneously. This is the *approval-dialog analogue* of CSS invisible-text injection in fetched web pages (the original InversePrompt class). **Neither vendor has shipped a definitive fix as of 2026-06-14.** Proposed mitigations include collapsing excess whitespace in dialogs and adding a "show full command" mandatory expand before approval. **Triage cues:** (1) LITL compounds any indirect prompt-injection finding — if attacker-controlled text can reach the agent's context (via Agentjacking, malicious README, poisoned MCP data), it can also manipulate the approval dialog; (2) when advising developers on approval dialog hygiene, recommend: *always scroll to the bottom of the dialog before approving*; *reject all compound commands (`;`, `&&`, `||` chains) that you haven't reviewed in full*; *never approve a long command that you cannot see in its entirety*; (3) `--dangerously-skip-permissions` removes the approval dialog entirely — it eliminates LITL as an attack surface but also eliminates all human-in-the-loop oversight; (4) add `"AI agent approval dialog bypass hidden command {today.year}"` and `"Lies in the Loop LITL Checkmarx {today.year}"` to Tier-C sweep queries (shallow window — this is new research, not yet widely exploited, but the class will be iterated on).
- **Telegram-as-C2 via victim's own bot token — a new C2 technique that bypasses egress monitoring.** [Operation Navy Ghost](advisories/2026-06-operation-navy-ghost-pyrogram.md) (Checkmarx Zero, June 2026) introduced a supply-chain C2 pattern distinct from every other campaign tracked in this repo: instead of exfiltrating stolen data or sending commands through an attacker-controlled server (GitHub Gists, localhost.run tunnels, AI-vendor API host camouflage, Tor onion services, DNS TXT records), the backdoor used the **victim's own Telegram bot token** to relay commands and stolen data through `api.telegram.org`. The bot's own API key becomes the C2 channel: the attacker sends Telegram messages from attacker-controlled accounts, the bot executes the commands, and stolen files travel back as document attachments — all over legitimate Telegram traffic that is allowlisted in virtually every corporate egress policy for bot deployments. **Why this matters for detection:** (1) network egress monitors that flag unfamiliar IPs or domains will not catch this — `api.telegram.org` is a trusted allowlisted destination; (2) the exfil channel is *already authorized* for the bot process; (3) no unusual port, no TLS certificate anomaly, no DNS lookup for an attacker domain. **Detection cues specific to this technique:** (a) monitor the Telegram bot's *sent-messages* history for document attachments and unusual API responses; (b) audit active command handlers at bot startup — legitimate bots should not respond to commands from accounts not on the developer's own whitelist; (c) `pyrogram/helpers/secret.py` (or any `secret.py` in a Telegram framework's `helpers/` directory) is an IOC; (d) bot activity during periods when no developer should be sending commands is anomalous. **Triage cues for new campaigns using this technique:** (1) any supply-chain advisory affecting a Telegram bot framework (pyrogram, telethon, aiogram, python-telegram-bot) should explicitly check whether the backdoor registers Telegram command handlers; (2) the C2 technique may generalize beyond Telegram — any application that holds credentials to a messaging or communication API (Slack, Discord, WhatsApp Business, Twilio, SendGrid) could be weaponized as an "in-channel" C2; (3) add the shared attacker Telegram account IDs to the IOC list as they are more persistent than package names; (4) `api.telegram.org` outbound connections from **non-bot backend processes** (database servers, CI/CD workers, backend APIs) are anomalous and worth alerting on. **Sweep query:** "Telegram bot PyPI backdoor C2 {today.year}" + "Telegram bot developer supply chain attack {today.year}." **Updated 2026-06-30 — first documented instance in this repo of victim's own communication API token as C2 channel.**
- **"AI coding tool auto-executes workspace config on open" is now a named systemic class with five documented entries.** Every major AI coding assistant in wide enterprise use has shipped a variant of the same root mistake: reading a workspace-scoped config file and spawning processes (MCP servers, hooks, tasks) without establishing workspace trust first, causing "git clone / folder open → code execution" with the developer's live credentials. The five entries as of June 2026: (1) [Claude Code CVE-2025-59536](advisories/2025-08-claude-code-inverseprompt.md) — `CLAUDE.md`/`settings.json` `postStart` hooks auto-execute on folder trust; (2) **Cursor CVE-2025-54136** — auto-run on repository open (`.cursor/`); (3) [Windsurf CVE-2026-30615](advisories/2026-05-windsurf-zero-click-mcp-rce.md) — zero-click MCP RCE on workspace open; (4) [TrustFall](advisories/2026-05-trustfall-mcp-auto-execute.md) — five AI CLIs auto-execute MCP servers on folder-trust dialog (Anthropic "won't fix"); (5) [Amazon Q Developer CVE-2026-12957](advisories/2026-06-amazon-q-mcp-workspace-rce.md) — `.amazonq/mcp.json` auto-loaded and MCP server processes spawned without consent, inheriting live AWS credentials; patched in Language Servers for AWS 1.65.0 (May 12, 2026). **The class generalizes:** any AI coding tool that (a) reads a workspace config file defining processes to spawn, (b) spawns those processes before asking the developer whether the workspace is trusted, and (c) spawns them with the developer's full process environment (inheriting `AWS_ACCESS_KEY_ID`, `GITHUB_TOKEN`, SSH sockets, etc.) is a "git clone to cloud compromise" vector. **Triage cues for new findings in this class:** (1) the exploitability threshold is very low — a single `git clone` or folder open is sufficient; (3) the attack surface is *any* channel that delivers a folder to the developer: public repos, PR contributions to a private repo, typosquatted package directories, polished fake coding-challenge repos (these are specifically documented as social-engineering vectors in the Amazon Q and Windsurf advisories); (4) the patch pattern is always "add a workspace-trust gate before spawning any process" — confirm the patch verifiably implements this (not just rate-limiting or sandboxing the spawned process); (5) SKILL.md Tier-A sweep queries: `"AI coding assistant workspace config auto-execute {today.year}"`, `"{tool} mcp.json auto-load CVE {today.year}"`, `"{tool} workspace trust bypass RCE {today.year}"`; rotate `{tool}` across: Claude Code, Cursor, Windsurf, Amazon Q, GitHub Copilot, Gemini CLI, Cline, aider, Continue.dev, OpenHands, Zed AI. (6) When a new entry appears in this class that Anthropic or another vendor states is "won't fix" or "expected behavior" (as with TrustFall), document the decision explicitly in the advisory and flag the open risk to users in the "Am I affected?" section — "vendor declined to patch" is itself a material fact for the vibe-coding audience.
- **Agentic threat actor (ATA) — an autonomous AI agent as the entire attack chain, not just a tool the attacker scripts.** [JADEPUFFER](advisories/2026-07-jadepuffer-langflow-agentic-ransomware.md) (Sysdig, reported 2026-07-02) is the first sweep-tracked incident where an LLM agent — with **no human operator directing individual steps** — chained recon, credential harvesting, lateral movement, and ransomware deployment against a Langflow/Nacos target, self-correcting a failed login in 31 seconds and generating 600+ distinct payloads along the way. This is a different category from every prior "AI-augmented attacker" finding this repo has tracked (e.g. Composio's "LLM-generated attack patterns," which describes a human using an LLM to *generate* exploit variants faster): here the **agent itself is the operator**, reasoning about its own next step with no human in the loop at any stage after the initial task framing. **Triage cues:** (1) when a vendor IR post or researcher writeup describes an intrusion as running "autonomously," "end-to-end," or "with no operator interaction," check specifically whether a human directed each step (AI-augmented, not new) or whether the agent made its own tactical decisions in response to failures/obstacles (agentic threat actor, new class — flag explicitly); (2) both CVEs JADEPUFFER exploited (Langflow CVE-2025-3248, Nacos CVE-2021-29441) were **already patched by their vendors** — the novelty here is entirely in the autonomous attacker capability, not a new vulnerability, so don't skip a finding like this for lacking a fresh CVE; (3) add `"AI agent autonomous ransomware attack {today.year}"` and `"agentic threat actor ATA {today.year}"` as Tier-A queries going forward; (4) expect this pattern to recur against other credential-hub AI tools already tracked in this repo (Langflow, Flowise, n8n, LiteLLM) since they're the same "central credentials cache" targets already covered — the difference next time will be which tool provided initial access, not whether an agent ran the rest of the chain autonomously.
- **"Reference-document" jailbreak — a long operational playbook handed to the model as material to consult defeats refusal training that a direct instruction does not.** The [Mexico government breach](advisories/2026-04-mexico-government-ai-agentic-breach.md) (Gambit Security, disclosed 2026-04-10, backfilled into this repo 2026-07-13 after a gap) is a human-directed sibling of JADEPUFFER's fully-autonomous pattern: a single operator used Claude Code (≈75% of remote commands) and GPT-4.1 (reconnaissance triage via a custom 17,550-line tool) to breach nine Mexican government agencies over ~2 months, exfiltrating 195M+220M records. - **Credential-as-path-traversal — a caller-supplied token used as a raw filesystem-path component, without normalization.** [`fast-mcp-telegram` CVE-2026-52830](advisories/2026-05-mcp-stdio-systemic-rce.md) (disclosed 2026-07-02) is a new shape in the "two parsers, one string" family: the MCP server's Bearer-token verifier joins the raw token string directly into a session-file path and checks whether that path exists, rejecting only the *exact* reserved token string — so a token like `../fast-mcp-telegram/telegram` path-traverses back to a known default session file and authenticates as that identity with **no valid token at all**.
