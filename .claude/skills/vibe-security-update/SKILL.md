# vibe-security-update

You are running a fresh sweep of vibe-coding-relevant security incidents and integrating findings into this repo. The repo is `vibe-coding-security/` and you are at its root.

## Output for the user (always include at end)

A 5-line summary:
1. Date of this sweep
2. # of new advisories added
3. # of existing advisories updated (status, IOCs, sources)
4. # of new sources discovered + added to priority list
5. Link to commit (if pushed)

## Source-priority semantics

The `source-priorities.json` schema:

```json
{
  "version": 1,
  "last_updated": "YYYY-MM-DD",
  "notes": "Higher weight = query first / trust faster. Cap 20. Min 1.",
  "sources": {
    "<domain>": {
      "weight": <int 1-20>,
      "hits": <int>,
      "last_hit": "YYYY-MM-DD" | null,
      "ecosystems": [<str>...],
      "tier": "vendor" | "research" | "aggregator" | "independent" | "official"
    }
  }
}
```

Use `weight` to:
- Pick top 10 sources for the `allowed_domains` filter in deep-tier queries
- Decide whether a single-source claim is trustworthy (weight ≥ 12 = OK to start a draft; lower = wait for second source)

## Constraints & cautions

- **Don't fabricate.** If a candidate incident doesn't have ≥2 independent sources, mark it `status: unconfirmed` in a new advisory and link only the sources you have. Do not invent IOCs, package names, or version numbers.
- **Verify dates against `today`.** Use `Today's date is YYYY-MM-DD` from the system context as ground truth, not the model's intuition.
- **Cap output.** If a sweep finds more than 10 candidate incidents, prioritize by severity × audience overlap with vibe coders. Log skipped ones in `runs.log.md` under "Notes: deferred".
- **Don't touch playbooks/prevention** in a routine sweep — those are evergreen. If you find a new attack pattern that warrants a new playbook, flag in `runs.log.md` under "Notes: playbook backlog" and let a human decide.
- **Don't auto-resolve status to `patched`** unless a vendor explicitly says so in a primary source.
- **Treat AI-agent framework CVEs as time-critical.** As of 2026-Q2, baseline disclosure-to-exploit is < 4 hours (per Sysdig honeypot data on PraisonAI). Prioritize these in triage and write them up same-day even if only 2 sources are available.
- **Cross-link cross-ecosystem worms — and Rust/Crates.io is now in scope.** When the same threat actor or payload appears in multiple ecosystems, cross-link the advisories explicitly (see Mini Shai-Hulud: TanStack ↔ PyTorch Lightning). Don't let the npm advisory and the PyPI advisory live in isolation. The campaign list now routinely spans **npm (`postinstall`) ↔ PyPI (import-time exec) ↔ Crates.io (`build.rs` build script)** — TrapDoor (May 2026) shipped all three from one actor in timed waves. When you see a cross-ecosystem stealer, check whether there's a Rust crate arm using `build.rs`, and whether the same campaign marker / GitHub account / Gist exfil endpoint appears across registries.
- **AI-agent config + skill files (`.cursorrules` / `CLAUDE.md` / `AGENTS.md` / `SKILL.md`) are a write-target, not just a read-target.** Earlier incidents *read* AI-tool config to steal creds (Bitwarden CLI AI-tool collector; Nx Console `~/.claude/settings.json` theft). TrapDoor (May 2026) inverts it: a malicious package **writes a hidden prompt-injection instruction into the repo's `.cursorrules` / `CLAUDE.md`**, hidden with **zero-width Unicode**, so the developer's *own* agent re-runs the attack on its next invocation (exfiltration disguised as an "automated security scan"). This fuses the GlassWorm steganographic-Unicode technique with AI-config-as-persistence/re-infection. The class has been formalized by the **Cloud Security Alliance "Agent Context Poisoning: SKILL.md and the New AI Supply Chain Attack Surface"** research note (2026-05-06) — payloads are natural-language behavioral instructions interpreted by models at runtime, not machine code, so static analysis and sandboxing don't catch them. Triage cues: on any supply-chain or repo-compromise finding, ask **"did it touch an agent-instruction file?"**; offer the grep-for-invisible-Unicode heuristic over `.cursorrules`/`CLAUDE.md`/`AGENTS.md`/`SKILL.md`/`.github/copilot-instructions.md`/`.windsurfrules`; and advise readers to keep those files in version control and diff them on every dependency change. This is a vibe-coding-specific surface — write such incidents up even when the headline is "another crypto stealer," because the AI-config persistence is the part our audience won't see coming.
- **Decorator-as-documentation pattern.** Watch specifically for vulnerabilities where an SDK annotation (`[KernelFunction]`, `@tool`, `@function_tool`, FastAPI's `@app.get`) is treated as documentation rather than a security boundary. This is now a known recurring class. When you see one, look for sibling vulnerabilities in the same SDK.
- **"Two parsers, one string" class (argv-smuggling + resolver disagreement + reconstructed-URL disagreement + check-vs-effect scope disagreement).** A recurring root cause: two components disagree on how to interpret the same value, and the security check runs on the *wrong* interpretation. Four known shapes now: (1) **Argv-smuggling / pre-parser** — an "eager" pre-parser walks `process.argv` for a flag (Claude Code's `eagerParseCliFlag`, Cursor's auto-run built-in handling) without tracking whether the matched string is itself the *value* of another flag, so an attacker controlling any argv element (deeplink, URL handler, MCP tool reply) smuggles arbitrary flag values. (2) **Matcher-vs-resolver disagreement** — an allowlist matcher and the OS/network resolver disagree on where a hostname ends, e.g. Claude Code's **SOCKS5 null-byte bypass** (`attacker.com\x00.google.com` passes the `.google.com` suffix check, the OS truncates at `\x00` and dials `attacker.com`, May 2026). (3) **Reconstructed-URL vs canonical-scope disagreement (host-header bypass)** — auth middleware reads a *rebuilt* URL (`request.url.path`, built from the `Host` header), the router reads the *canonical* ASGI scope path (`scope["path"]`), and a malformed `Host: foo?` re-splits the URL so they diverge — auth check runs on the wrong path while the protected endpoint still gets dispatched. **Starlette BadHost CVE-2026-48710 (May 2026)** is the framework-level case; downstream FastAPI/vLLM/LiteLLM/Python-MCP-SDK/TGI/OpenAI-proxy apps that authorize on `request.url.path` are vulnerable until they upgrade to Starlette ≥ 1.0.1 *or* refactor middleware to use `request.scope["path"]`. (4) **Check-vs-effect scope disagreement** — a deny-list / permission check binds to *current* (mutable) workspace/scope state, but agent input can rewrite that state before the operation runs, so the permission check evaluates against a *different* scope than the operation actually uses. **Windsurf CVE-2025-62353 (Oct 2025)** is the cleanest case: README.md prompt-injection rewrites Cascade's workspace path to `/`, then `write_to_file` targets arbitrary paths — **even with Auto-Execution OFF and `write_to_file` on the explicit deny list** (the deny check evaluated the rewritten scope). Same shape in any agent that lets agent-readable content mutate the scope of subsequent security checks. Note the discovery vector for BadHost — X41 D-Sec found it during an OSTIF-sponsored vLLM source-code audit, then realized it was a framework-level bug below vLLM — so an audit of any single downstream consumer of Starlette is implicitly an audit of the framework; flag this when sweep results name an Alpha-Omega / OSTIF audit. Same family as the InversePrompt cluster. **General triage cue: whenever the framework hands you both a canonical and a derived/reconstructed value of the same thing, the canonical one is the security boundary** — argv structure, post-canonicalization path, `scope["path"]`, the bytes that will actually hit `connect()`, the user-confirmed-at-session-start workspace path. **And: when a security check evaluates state that the operation it's gating can also mutate, the check is a permission honeypot, not a permission boundary** — bind security decisions to immutable scope, or re-check after any scope-changing input. Look for this whenever a value crosses a boundary between an in-app validator and a lower-level executor/resolver/dispatcher (argv parser, DNS, SOCKS, shell, path canonicalizer, ASGI router, workspace-scope manager).
- **AI-tool OAuth pivot pattern.** A breach at a third-party AI productivity tool that holds Workspace/Drive/GitHub OAuth grants is upstream of every cloud account that authorized it. The Vercel/Context.ai April 2026 incident is the first widely documented case; expect more. When triaging an AI-vendor breach disclosure, check what *other* platforms the breached tool had OAuth into — those are downstream victims.
- **Vendor patched ≠ patched.** If a vendor ships a fix that adds approval prompts or alerts but leaves the underlying trust-boundary intact (cf. ClaudeBleed v1.0.70), the correct status is `mitigated`, not `patched`. Don't auto-promote based on "vendor released a version." Read the researcher's follow-up and confirm the structural fix.
- **Silent patch (no CVE/advisory) ≠ no incident.** Some vendors fix security bugs quietly — no CVE, no advisory, no changelog note. Claude Code's network-sandbox **SOCKS5 null-byte bypass** was fixed in v2.1.90 (2026-04-01) with zero disclosure; it was the *second* silently-patched Claude Code sandbox bypass in ~5 months (prior: CVE-2025-66479). Implications for the sweep: (1) a "silent fix" disclosure (usually from the finding researcher's own blog weeks later) IS a writeable incident — set `status: patched` but call out the silent handling and the unprotected window; (2) advise readers to keep AI tools on `latest` and not pin old versions, because **"latest" carries undisclosed security fixes you can't see in release notes**. When a researcher blog says "they fixed it quietly," diff the fixed vs. prior version to confirm and record the vulnerable version range.
- **Connector-chaining lethal trifecta in desktop AI apps.** When an AI desktop app (Claude Desktop, Cursor, etc.) lets the model autonomously compose connectors, a low-trust *reader* connector (calendar, email, Drive, web) piped into a high-trust *executor* connector (a local MCP server that runs shell/code) collapses the lethal trifecta into one app — a malicious calendar event + a vague prompt ("take care of it") = zero-click RCE (Claude Desktop Extensions / DXT, CVSS 10.0, LayerX; Anthropic declined to fix as "outside our threat model"). Triage cue: on any AI-desktop/IDE finding, ask whether reader and executor connectors share one trust domain, and whether the vendor's response is "won't-fix / out of threat model" (→ `status: active`, not `mitigated`). Siblings: Supabase MCP lethal trifecta, Windsurf zero-click MCP.
- **AI-agent → AI-agent supply chain.** Recurring: one compromised AI tool installs a second AI agent on victims (Clinejection → OpenClaw via npm postinstall; Comment and Control → exfil via Claude Code Sec Review). When you find a compromised AI dev tool, check whether the payload installs *another* known AI agent — cross-link both advisories.
- **Provenance is identity, not integrity.** Supply-chain worms now defeat provenance attestation in two ways: (1) hijacking a real release pipeline mid-build so the *legitimate* pipeline signs a malicious artifact (TanStack/Mini Shai-Hulud, May 11 2026 — first valid SLSA provenance on malicious npm), and (2) **self-minting cryptographically valid Sigstore attestations** with an ephemeral EC keypair + OIDC identity token, so every republished package shows a green "verified provenance" badge and passes standard verification (@antv/durabletask wave, May 19 2026). A green provenance/SLSA badge proves *who* built an artifact, **not that it is safe** — never treat it as a clean signal. Look for this whenever a worm "republishes under legitimate maintainer identity."
- **Poisoned IDE/editor extension as a platform-breach vector.** A malicious version of an editor extension (VS Code / Cursor / Windsurf / Open VSX) on a single developer's machine is a foothold into every repo and credential that editor touches. TeamPCP used exactly this — the trojanized **Nx Console** extension (`nrwl.angular-console@18.95.0`, May 2026) — to exfiltrate ~3,800 of GitHub's *own* internal repos. Same trust-transfer shape as the Amazon Q wiper and postmark-mcp (build trust over clean versions, then push one poisoned release) and a sibling of the AI-tool OAuth-pivot class. When triaging an "AI/dev tool was compromised" story, check whether the delivery vector was an extension marketplace, and whether silent auto-update carried the payload. Note also: extension payloads now specifically target **AI-tool config** (`~/.claude/settings.json` and similar) alongside cloud creds — flag that as its own IOC.
- **Cross-incident credential chaining (trace the leaked token forward).** Stolen credentials don't stay in their original incident. The Nx Console compromise happened because an Nx contributor's GitHub token leaked in the *prior* TanStack/Mini Shai-Hulud wave, then got reused a week later to publish the poisoned extension, which became the foothold for the *downstream* GitHub internal-repo breach — three "separate" incidents that are one chain. Sweep discipline: when a wave dumps credentials, ask **"whose token was stolen, and what can it publish next?"** and proactively check the maintainers/orgs named in a credential-theft wave for follow-on registry/extension compromises. Cross-link the chain explicitly (token-leak advisory ↔ extension advisory ↔ breach advisory). **Credential cascades now have a documented infostealer-as-a-service intermediary:** [Megalodon](advisories/2026-05-megalodon-github-actions-mass-campaign.md) (May 2026) hit **5,561 GitHub repos in 6 hours** using stolen credentials, and Hudson Rock matched **~33% of affected accounts to known infostealer victims** — strongly suggesting the credentials came from the [GlassWorm](advisories/2025-10-glassworm-vscode-worm.md) ecosystem and were *re-sold* downstream. When you see a coordinated takedown (GlassWorm 2026-05-26 = CrowdStrike + Google + Shadowserver), expect a downstream credential-resale wave to follow within days from a *different* actor monetizing the harvest. **Hudson Rock + StealerCheck-style lookups against affected-username lists are now a primary correlation tool for the sweep** — when an aggregator names affected accounts, run them against the infostealer-victim corpus before attributing.
- **Source-repo compromise as a publish-time trust boundary.** The npm/PyPI account isn't the only publish-time boundary — the **GitHub source repo + its `.github/workflows/`** is the *other* one, and it's often weaker. [Megalodon](advisories/2026-05-megalodon-github-actions-mass-campaign.md)'s `@tiledesk/tiledesk-server` arm (npm 2.18.6 → 2.18.12, May 2026) is the cleanest worked example: the attacker never touched the npm account, just committed a single `.github/workflows/docker-community-worker-push-latest.yml` change (entire prior Docker-build workflow gone, replaced with `set +e; echo "..." | base64 -d | bash`), and the legit maintainer published from the poisoned source without spotting the swap. Sibling: [elementary-data](advisories/2026-04-elementary-data-pypi-ghcr-compromise.md) (Apr 2026, GitHub Actions script injection → forged signed release → real publish pipeline). Triage cue: on any package-poisoning finding, ask whether the entry point was the maintainer's **npm/PyPI token** *or* their **source repo `.github/workflows/` directory**. The signature pattern is a **single-file workflow change authored by a bot-named account** (`build-bot`, `auto-ci`, `ci-bot`, `pipeline-bot`, `dependabot[bot]`-lookalikes), especially one containing a base64-bash pipe or `workflow_dispatch` backdoor. The defensive pattern is **require signed commits + workflow-change code review on protected branches** (which would have failed verification for Megalodon's `build-bot`-authored commits).
- **Coordinated botnet takedown as a recognized advisory event class (`active` → `mitigated`, not → `patched`).** When CrowdStrike / Google / Shadowserver / law-enforcement-class actors disrupt a sweep-tracked campaign's C2, update the existing advisory's status to **`mitigated`** (NOT `patched` — the structural fix isn't on the vendor side) and document the takedown date and the disrupted channels. **Warn readers that the takedown does NOT uninstall malware, rotate stolen credentials, or undo downstream credential resale** — poisoned packages/extensions on disk and stolen creds in the wild are still live risks. The [GlassWorm 2026-05-26 takedown](advisories/2025-10-glassworm-vscode-worm.md) is the template: CrowdStrike Counter Adversary Operations + Google + Shadowserver Foundation hit all four C2 channels simultaneously (Solana blockchain memos + BitTorrent DHT + Google Calendar dead-drops + direct VPS IPs). The quad-redundant C2 architecture meant a less coordinated strike would have left survivors — when triaging future takedowns, **check whether ALL known C2 channels were disrupted simultaneously** before promoting status; partial disruption is a temporary reduction, not mitigation. Note: the [Megalodon wave](advisories/2026-05-megalodon-github-actions-mass-campaign.md) shows that credentials harvested before a takedown stay valuable downstream — the C2 may be dead, but the data it exfiltrated lives on forever in attacker-controlled archives.
- **AI-vendor code-signing-cert rotation as a recurring named-instance.** When a major AI vendor (OpenAI, Anthropic, Google AI Studio, etc.) is downstream of a supply-chain wave that touches **code-signing infrastructure**, the downstream impact is a *forced-update event* for every user of the affected desktop app. **OpenAI has rotated macOS signing certs twice in 5 weeks** (May–June 2026): [Axios](advisories/2026-03-axios-compromise.md) March 31 disclosure → May 8 revocation, and [TanStack/Mini Shai-Hulud](advisories/2026-05-tanstack-mini-shai-hulud.md) May 11 wave → June 12 revocation. Both involved a GitHub Actions workflow with access to macOS signing keys downloading a compromised npm dep through a **floating tag without `minimumReleaseAge`**. Affected products: ChatGPT Desktop, Codex, Codex-cli, Atlas. Triage cue: when a sweep result names "[AI vendor] employee compromised" or "[AI vendor] internal source repos accessed," **explicitly check whether code-signing keys or signing pipelines were exposed**, and look for an update-deadline mandate that will force every downstream desktop-app user to update by a specific date. Track these rotations in the advisory's downstream-impact table; users will hit "app stops working" breakage on the revocation date and ask for context.
- **Steganographic extension payloads + un-takedownable C2.** GlassWorm (Oct 2025 → 2026, recurring) hides its logic in **printable-but-non-rendering Unicode** (invisible to a human reviewer and to many diff tools) and pins C2 to a **Solana blockchain memo** (a censorship-resistant dead-drop) backed by direct-IP + Google Calendar fallbacks — so takedowns can't reach the control channel and the worm self-reseeds with every set of stolen publish creds. When triaging an extension/worm story, look for "invisible Unicode," "blockchain C2," "Open VSX," and "self-propagating," and offer a detection heuristic (grep for zero-width / variation-selector / bidi code points in extension source).
- **Incomplete fix ≠ patched.** A vendor shipping a version labeled "fixed" doesn't mean the hole is closed — confirm against a researcher's follow-up. Langflow 1.8.2 was widely reported as the CVE-2026-33017 patch but remained exploitable (JFrog); only 1.9.0 actually fixed it. When a "patched" version exists, search "{tool} {CVE} still exploitable / patch bypass / incomplete fix" before setting `status: patched`.
- **AI-agent skill/plugin marketplace poisoning.** AI agents now ship their own community "skill"/plugin marketplaces — **ClawHub** for OpenClaw (formerly Clawdbot/Moltbot), plus Claude Code skills, MCP registries, and the like. These are the npm/Open-VSX of the agent world and are usually **open-by-default**: ClawHub's only publish gate was a GitHub account one week old. - **Open-sourced/leaked worm → commoditized copycat wave.** When a threat actor *publishes the working source* of a supply-chain worm and/or runs a paid "biggest attack" contest (TeamPCP open-sourced Mini Shai-Hulud on 2026-05-12 + a $1,000 BreachForums competition), the barrier to a Shai-Hulud-class attack collapses to "clone the repo, swap the C2 key." - **AI-vendor-host camouflage exfil.** [Miasma](advisories/2026-06-miasma-redhat-cloud-services-compromise.md) (Jun 2026) is the first sweep-tracked wave to disguise stolen-credential POSTs as **outbound HTTPS to a real AI-vendor API host** — `https://api.anthropic.com:443/v1/api` (note: the `/v1/api` path doesn't exist, but the *request* itself carries the exfil payload; the 4xx response is irrelevant). This is the **DNS-baseline-normal counterpart to disposable-tunnel C2**: every org running Claude Code / Cursor / Anthropic API integrations already has outbound to `api.anthropic.com` allowed, monitored *only* for response codes, and not flagged as anomalous in egress logs. - **MCP servers are unauthenticated network services by default.** A growing class: a widely-used MCP server binds `0.0.0.0` with no auth in its HTTP transport, so any network-reachable attacker invokes its tools (nginx-ui MCPwn CVE-2026-33032; Atlassian `mcp-atlassian` MCPwnfluence CVE-2026-27825/-27826, 4M+ downloads, SSRF+arbitrary-write→root RCE; Azure MCP Server CVE-2026-32211 missing-auth info-disclosure + CVE-2026-26118 SSRF). - **Agent-platform-as-MCP-broker — a high-trust hub with massive fan-out.** Above MCP sits a class of platforms that *brokers* tool calls — Composio, LangSmith, Smithery / Pinecone Hub, AgentOps, NexusGenAI, Portkey, Helicone, OpenRouter — holding customers' OAuth grants and API keys for ~100 downstream services on their behalf. Much higher fan-out than the [Vercel/Context.ai](advisories/2026-04-vercel-context-ai-breach.md) AI-tool OAuth-pivot (single tool, single tenant) or the [Bitwarden CLI AI-collector](advisories/2026-04-bitwarden-cli-shai-hulud-third-coming.md) (cred-scraper module). Treat as a sibling of "AI-tool OAuth pivot" but distinct because the fan-out is the platform's *whole product*, not an incidental integration.
- **LLM-augmented attacker as an explicit category.** Earlier sweeps *inferred* AI augmentation from speed; [Composio's May 2026 disclosure](advisories/2026-05-composio-ai-agent-platform-breach.md) explicitly attributes attack pattern generation to LLMs ("brute-forcing many combinations of exploits using LLM-generated attack patterns"). Implications for the sweep: (1) defenders' rate limits and WAF signatures were calibrated against humans and are now under-scaled — an attacker with an LLM can produce 10,000 well-formed candidate exploits per minute; (2) "exceptional speed / deep knowledge of internal architecture" in a vendor IR post often correlates with LLM-augmented reconnaissance — if the vendor names it, record it; (3) AI-platform employees with broad-scope OAuth grants (Gmail / Workspace) are an outsized target because magic-link sign-in chains turn one stolen email account into platform admin. Watch for this language in vendor IR posts and quote it directly.
- **"Tool definitions are documentation" inside agent platforms is the new "decorator-as-documentation."** Where SDK annotations (`[KernelFunction]`, `@tool`, `@function_tool`) were treated as docs by Semantic Kernel and friends, agent *platforms* (Composio) treat **runtime tool-definition registration** the same way — `register_tool(name, handler)` is taken as an extensibility / docs primitive rather than a privileged write. The May 2026 Composio breach was the first widely-disclosed case where an attacker, having reached a sandboxed execution environment, **registered new malicious tool definitions** to chain privileges to arbitrary code execution. Triage cue: on any agent-platform / orchestration-framework finding, ask whether the platform exposes a tool-registration API to its own internal agents and whether that API is gated by code review / signed registration / rate limits — if not, that's the *write*-target analogue of `.cursorrules`/`CLAUDE.md`/`SKILL.md` on the developer side.
- **"Localhost is not a security boundary in the browser-attacker model."** A growing class of dev-tool / local-agent CVEs hinge on the assumption that "binds to 127.0.0.1, therefore safe." It isn't — the victim's *browser* trivially reaches `localhost`, and a single click on a malicious link delivered by any out-of-band channel (Slack, email, AI-tool chat, social) is an attack. **OpenClaw CVE-2026-25253 (Jan 2026)** is the cleanest worked example: the Control UI parsed a `gatewayUrl=` query parameter from the URL it was loaded with, repointed the WebSocket at an attacker-controlled gateway, leaked the auth token, and ran arbitrary shell commands — all from one bookmark, including against NAT'd / firewalled / IP-allowlisted instances. **OpenCode CVE-2026-22812 (Jan 2026)** is the second clean worked example, and adds two reinforcement points: (1) binding to **`0.0.0.0` instead of `127.0.0.1` makes this strictly worse** — any LAN device joins the browser-tab attack model, including anyone on the same Wi-Fi (so the "local-only" mental model fails in two ways: the browser reaches localhost, *and* the LAN reaches `0.0.0.0`); (2) **OpenCode CVE-2026-22813 packs a connector-chaining lethal trifecta into one app** — the chat UI inserts LLM markdown responses straight into the DOM (no DOMPurify, no CSP), and the privileged WebSocket-authorized `/shell` endpoint lives in the *same origin*, so any path that gets attacker-controlled text into an LLM response (poisoned file, fetched page, malicious git remote, MCP reply) is an RCE primitive. Sibling cluster: Open WebUI / Jupyter / Marimo / Langflow when bound to localhost without CSRF tokens or origin checks; many MCP servers when bound to localhost via HTTP transport. Triage cue on any local-agent UI / control-panel CVE: ask **(a) does the UI parse URL parameters or accept POSTs without CSRF tokens?**, **(b) does it apply those parameters as runtime config (gateway URL, MCP server, workspace path, settings file)?**, **(c) is there an Origin / Referer / SameSite check on state-changing requests?**, **(d) does the UI bind `0.0.0.0` or `127.0.0.1`?**, **(e) does the chat / markdown renderer reach into the same origin as a privileged WebSocket / shell / file-write endpoint, and if so, is the renderer sandboxed (CSP, DOMPurify, `<iframe sandbox>`)?** If any of (a)/(b)/(d) and not (c)/(e), that's a 1-click attack surface regardless of network topology. Cross-link with the agent-config-write-target caution (TrapDoor / Nx Console / Bitwarden CLI) and the connector-chaining-lethal-trifecta caution (Claude Desktop DXT — note that the executor connector can be *built into the same process* as the chat UI, not just a separately-installed MCP server) — all three classes share the same defensive pattern: never let agent-readable input (URL params, file contents, fetched pages, LLM responses) cross into the privileged-write / privileged-execute path without an explicit, immutable user confirmation.
- **AI/data tools shipping unauthenticated network RCE primitives is now a named cluster.** Five entries from Q1-Q2 2026: **Langflow CVE-2026-33017** (unauth flow-build endpoint → Python RCE) + **PraisonAI CVE-2026-44338** (auth disabled by default on legacy API server) + **Marimo CVE-2026-39987** (unauth `/terminal/ws` → PTY shell) + **LiteLLM CVE-2026-42208** (pre-auth SQL injection via `Authorization: Bearer` header) + **Flowise CVE-2025-59528 / Agent-node cluster** (`eval` on `mcpServerConfig` + Agent classes `eval` LLM-generated Python with no sandbox). - **`binding.gyp` / Phantom Gyp is a new install-time execution primitive that `--ignore-scripts` does NOT block.** The [Phantom Gyp wave](advisories/2026-06-phantom-gyp-miasma-wave4.md) (June 2026, fourth Miasma/Shai-Hulud copycat) established `binding.gyp` + node-gyp native-build as an install-time code-execution path that is **not suppressed by `npm install --ignore-scripts`**. Standard guidance tells developers to use `--ignore-scripts` to disable malicious `preinstall`/`postinstall`/`prepare` lifecycle hooks — but `binding.gyp` causes `npm install` to run `node-gyp build` as a native-addon compilation step, which executes attacker-controlled scripts regardless of the `--ignore-scripts` flag. The four known install-time primitives are now: (1) `preinstall`/`postinstall`/`prepare` lifecycle hooks (blocked by `--ignore-scripts`); (2) import-time exec in PyPI packages (`.pth` files, top-level code); (3) `build.rs` in Rust/Crates.io crates (runs at compile time); (4) **`binding.gyp`** in npm packages (runs `node-gyp build`, not a lifecycle script, not blocked by `--ignore-scripts`). **Triage cue:** any npm package that includes `binding.gyp` but is not a well-known native addon (node-sass, bcrypt, sharp, fsevents, canvas, grpc, leveldown) should trigger review. Detection commands: `grep -r '"binding.gyp"' node_modules/*/package.json | grep -v node_modules/known-native-addon`; and look for `binding.gyp` files in unfamiliar packages. When recommending `--ignore-scripts` in advisories, **add a note** that it does not block binding.gyp-triggered execution. **Sweep discipline:** add a dedicated Tier-A query for "binding.gyp node-gyp supply chain npm malicious {today.year}" on every run. **Upcoming platform fix: npm v12 (expected July 2026)** will set `allowScripts: off` by default, disabling both lifecycle scripts AND `binding.gyp`-triggered builds in one change — the first npm version to fully block this primitive. Until npm v12 is universally adopted, the caution above applies. When npm v12 ships, update advisories that recommend `--ignore-scripts` to note that upgrading npm is now sufficient (and the preferred fix), and check for a new Tier-A query window around "npm v12 allowScripts bypass" to detect any regression or bypass discovered against the new default.

- **IronWorm — Rust ELF binary + eBPF kernel rootkit + Tor C2 as a supply-chain worm capability escalation.** [IronWorm](advisories/2026-06-ironworm-npm-rust-ebpf.md) (June 2026) established a new capability tier above the JavaScript-based Shai-Hulud/Miasma lineage: instead of a Node.js/Shell payload, it drops a **Rust-compiled ELF binary** (cross-compiled for 50+ target architectures) that installs an **eBPF kernel rootkit** — capable of hiding processes, files, and network connections from the same eBPF-based EDR and observability tools (Falco, Tetragon, Cilium, Datadog Agent) used to detect the older JavaScript payloads. - **Workflow-automation / iPaaS tools as a "workflow broker credential hub" attack surface.** [n8n Ni8mare](advisories/2025-11-n8n-ni8mare-rce.md) (CVE-2026-21858, CVSS 10.0, Nov 2025) established the workflow-automation class as a high-value target in the same "central credentials cache" cluster as Composio, LangSmith, Flowise, Langflow, and LiteLLM: n8n workflows hold **OAuth tokens and API keys for dozens of downstream services** (GitHub, Slack, Gmail, HubSpot, Stripe, Jira, Notion, databases, webhooks) in one execution environment. A pre-auth RCE gives an attacker the union of every connected service's access. **Key pattern**: any workflow-automation / no-code / low-code platform that (a) ships its own execution server, (b) stores credentials for downstream services, and (c) exposes an admin UI reachable from the public internet, has the same blast-radius profile as an AI proxy or agent-orchestration platform — potentially higher fan-out because the downstream connections are *intentional wide integration surface*, not incidental to the AI use case. **Triage cue**: when a "no-code/low-code workflow automation RCE" surfaces, immediately ask "how many downstream OAuth connections does the average deployed instance hold?" — if > 5, treat it as a credential-hub attack, not a standalone web CVE. n8n Ni8mare had CVSS 10.0 + a follow-on CVSS 9.4 authenticated-bypass CVE with public exploits within 6 weeks — treat n8n (and n8n-class tools) with the same urgency as AI-framework CVEs. Add to Tier-B vendor rotation (see above).
- **Registry bypass via GitHub source-repo commit + AI-tool config hook auto-execution (Miasma Wave 5 class).** [Miasma Wave 5](advisories/2026-06-miasma-wave5-microsoft-azure-github.md) (June 5, 2026 — 73 Microsoft GitHub repos + 5 mantine-datatable repos) established a new attack class: **no npm/PyPI package is published at all.** Instead, stolen credentials from a prior supply-chain wave are used to push a malicious commit directly to a source repository. The commit plants a **4.3 MB payload runner** (e.g., `scripts/monitor.mjs`) and wires it to auto-execute via **five developer-tool hook mechanisms simultaneously**: (1) **Claude Code** — `.claude/settings.json` `postStart` hook; (2) **Gemini CLI** — `GEMINI.md` `postToolUse` hook; (3) **Cursor** — `.cursor/prompts/autorun.cursorrules` auto-run; (4) **VS Code** — `.vscode/tasks.json` background task; (5) **npm test hook** — `package.json` `"test"` script override. A developer who clones or opens the poisoned repo and launches any of these five tools will trigger the payload **without running `npm install`** — no `postinstall`, no `binding.gyp`, no install step at all. The payload then harvests credentials and self-propagates using the developer's own npm/GitHub tokens. **Triage cues**: (1) on any "source repository compromise" finding (not just npm/PyPI), **immediately check the five hook paths** (`.claude/`, `.cursor/`, `.vscode/tasks.json`, `GEMINI.md`, `package.json` `test` field) for newly committed scripts; (2) `git log --since="<compromise-date>" --all --oneline -- .claude/ .cursor/ .vscode/tasks.json GEMINI.md package.json` is the first responder query; (3) the Wave 5 campaign used credentials stolen in the Wave 4 (Phantom Gyp) binding.gyp wave — when a credential-theft wave completes, **proactively check source repos of orgs whose GitHub tokens were exposed** for AI-tool hook modifications, not just their npm registry accounts; (4) **grep for zero-width Unicode in all hook-path files** (`grep -rP '[\x{200B}-\x{200D}\x{FEFF}\x{00AD}]' .claude/ .cursor/ CLAUDE.md GEMINI.md`) — the class fuses TrapDoor-style steganographic concealment with AI-tool-config-as-persistence. **Advisory implication**: this class requires expanding the "Am I affected?" detection surface in future advisories to always include the five hook paths, not just the registry check. **Sweep discipline**: when a sweep result mentions a GitHub source-repo compromise (not just a registry package publish), classify it as `advisories/` worthy even if the package count is 0 — the payload-delivery mechanism is the hook files, not the npm entries.
- **Registry-side hygiene matters as much as client-side (build-system primitives are supply-chain primitives).** [Cargo CVE-2026-5223](advisories/2026-05-cargo-symlink-sparse-url-cves.md) — symlink-override that lets a malicious crate overwrite the cached source of another crate in the same registry — affects every Cargo before Rust 1.96.0, but **crates.io users are NOT affected** because crates.io rejects symlinks at upload time. Generalizes a recurring lesson: registry-level enforcement closes the same primitive that client-level extraction misses. Use this as a triage / framing cue when writing up archive-extraction CVEs (symlinks, ZIP-slip, path traversal): always note whether the public registry server-side blocks the primitive, and whether self-hosted / corporate registries do the same. The general statement: **every archive-extraction primitive a client doesn't guard is one a registry can guard server-side, and vice-versa — defense in depth across both layers.** Examples: npm registries can reject `postinstall` from anonymous publishers / first-week accounts; PyPI mirrors can reject `*.pth` top-level files in uploaded wheels (the [elementary-data](advisories/2026-04-elementary-data-pypi-ghcr-compromise.md) primitive); private Cargo mirrors can reject symlinks; container registries can reject layers that contain setuid binaries.
- **GitHub issue spam as a supply-chain package-discovery vector (FakeFix class).** The [Solana FakeFix Campaign](advisories/2026-06-solana-fakefix-campaign.md) (June 2026) introduced a new social-engineering primitive: **planting fake GitHub issues** on high-traffic legitimate repositories (Solana SDK, @solana/web3.js, Anchor) that describe a plausible developer error, then direct the searcher to install a malicious "fix" package. This is distinct from: (1) **typosquatting** (targets registry search-box SEO — attacker owns a package with a misspelled name); (2) **slopsquatting** (targets LLM hallucination — attacker registers packages an AI model invents); (3) **dependency confusion** (targets private registry resolution order). The **FakeFix class** targets the **help-seeking surface**: a developer googles their error message, lands on a GitHub issue thread that looks like a resolved ticket, and installs whatever `npm install` command the "helpful commenter" posted. The key IOC is `github.com/[legitimate-repo]/issues/[N]` with a comment pattern: (a) user reports an exact error, (b) commenter says "try this", (c) commenter edits their original comment to add a different (malicious) install command after the issue gains organic views. **Triage cues:** (1) add `"github issue spam supply chain npm {today.year}"` as a Tier-A query on every sweep; (2) when a new malicious package is disclosed, check whether its discovery vector was a GitHub issue thread — if so, find and link the fake issue(s) in the advisory; (3) the FakeFix technique pairs naturally with wallet-targeting campaigns (Solana ecosystem in June 2026) and with MCP-developer-targeting (both involve high-trust search behavior); (4) an IOC is a GitHub issue comment from an account created within days of posting, with no prior issue history, on a high-traffic library repo, that contains an `npm install` or `pip install` command — these typically get removed within 24–72h of disclosure, so cache the URL in the advisory immediately.
- **Fake developer-monitoring service telemetry as exfil camouflage.** The [onering Rust crate compromise](advisories/2026-06-onering-rust-crate-compromise.md) (June 2026) introduced a variant of the AI-vendor-host camouflage pattern: the `build.rs` payload disguised its exfil as an **HTTP POST to an endpoint formatted like a Sentry SDK error-report webhook** (`POST /api/<project>/store/` with `X-Sentry-Auth` headers). Sentry telemetry is baseline-normal egress in virtually every CI/CD environment, and many orgs' egress monitors don't inspect Sentry POST bodies. This generalizes the technique named in the [Miasma advisory](advisories/2026-06-miasma-redhat-cloud-services-compromise.md) (`api.anthropic.com` camouflage): any trusted developer-tooling endpoint can be the camouflage host — **the attacker picks the service most likely to be whitelisted in the victim's egress monitor**. Extended list of camouflage host classes: (1) AI-vendor API hosts (`api.anthropic.com`, `api.openai.com`, `generativelanguage.googleapis.com`); (2) error-monitoring / APM webhooks (Sentry `store`, DataDog agent, New Relic, Honeycomb, OpenTelemetry collector); (3) CDN/analytics endpoints (Cloudflare analytics, Segment, Mixpanel). **Detection cues:** (a) alert on outbound `POST` to monitoring-service hosts from workloads that don't run the monitoring agent; (b) flag non-2xx responses to Sentry/APM hosts at unexpected intervals (real telemetry is batched; exfil camouflage tends to fire once at `build.rs` or `postinstall` time); (c) when writing up a `build.rs`/`postinstall` exfil finding, **look at the destination URL format** — if it matches a developer-monitoring service webhook, call out the camouflage technique by name and add it to the IOC list. **Sweep discipline:** on any new `build.rs` or install-hook exfil report, run a regex match on the destination URL against known monitoring-service API patterns before accepting "unknown C2" as the description.
